## Top 5 issues, in priority order

1. **P0 — `db:verify:dispatch` fails live, and it fails exactly on the path this audit most needed to exercise.** `scripts/verify-agent-dispatch.mjs:395` calls `projects.freeze_scope_version` and gets `not_authorized` instead of `frozen`. Root cause, read directly from `supabase/migrations/20260921190000_a_client_could_move_the_baseline.sql` (lines 1–38): a **real, already-committed security fix** landed today that adds `core.can_manage_delivery()` checks to `open_scope_version` / `freeze_scope_version` / `submit_change_request` / etc., closing a genuine exploit (`client_admin` portal role could previously freeze scope and open change requests directly via PostgREST). Good fix — but the dispatch test script's actor was never updated to satisfy the new check, so it cascades into 6 more false failures: the `ui_designer` L2 dispatch on `scope.frozen` (screen-inventory generation, exactly Phase 3's entry trigger — `D2b` block) and the QA planning dispatch off the same event (`D2d` block) **could not be exercised live in this pass**, because the baseline never froze. This is not a Phase 3 defect — it is test-script staleness following a legitimate Phase-2-adjacent security patch — but it means the "ui_designer L2 autonomously drafts screen inventory" claim in the traceability doc (G-302/G-303) is currently **IMPLEMENTED_UNVERIFIED**, not proven, in this environment. Fix: give the dispatch script's test actor `can_manage_delivery()` (or call as an internal role) before freezing scope, then re-run.
2. **P1 — Scope-change escalation hand-off is manual, undocumented as such in the checklist's own language.** `possible_scope_change` correctly stops the phase into `scope_escalation` with the client's exact words preserved (`20260919140000`), which is the safety-critical half. But nothing creates the actual `change_requests` row automatically — a person does it. The Master PDF's §17 ("route to the appropriate requirement/scope/change workflow") is satisfied only up to the stop; the routing itself is manual. Not a defect, but should be stated as MANUAL_EXTERNAL rather than EXISTS in the next revision of the traceability doc so nobody mistakes "escalated" for "handled."
3. **P1 — Admin Panel is missing 5 of 13 required surfaces**, most importantly **Theme Studio**, **Color Studio**, and a dedicated **Final Selection** view (traceability doc's own table, spot-checked against `page.tsx`/`design-forms.tsx`, still accurate). The rows, triggers, and refusal logic backing all of these exist and are enforced at the database layer (confirmed live), but an Admin cannot yet *see* every theme/color option that was generated from a UI screen — only through raw table access. This is a real usability gap against Master §8's locked "visible from the Admin Panel" principle, even though nothing is silently happening — it's DISCONNECTED (data exists, no consuming surface) rather than MISSING outright.
4. **P2 — Client reference attachments have no binary upload path.** `client_reference` (a `ClientDesignDecision` classification) accepts only a URL or a text note, never a file. Low severity for a design-direction phase but worth flagging for Phase 4 planning since actual mockup/screenshot references from clients are common in practice.
5. **P2 — History-freeze trigger for the final lock was flagged MISSING in the traceability doc**, but that matrix was written before several 2026-09-21 migrations landed (including today's `20260921190000` security fix and `a_client_could_move_the_baseline`). I did not get to re-verify this specific claim against a raw `pg_trigger` read before the environment had to be torn down — recommend a fast follow-up: `select * from pg_trigger where tgrelid = 'projects.phase_three_handoffs'::regclass` (or equivalent) to confirm whether an UPDATE/DELETE-blocking trigger actually exists now, since the traceability doc may be stale on this one point.
