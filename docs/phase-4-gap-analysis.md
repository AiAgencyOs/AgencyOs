# Phase 4 Gap Analysis

Companion to `docs/phase-4-implementation-traceability.md`. Read-only audit performed 2026-09-26 against the 7 Phase 4 spec PDFs in `phase 4/` and the current repo state (through commit `03d25b4`). No code, migrations, or files were changed except these two documents.

## Executive summary

Phase 4 asks for six coordinated agents (PM, UI Designer, Prototype, QA/Prototype Validation, Orchestrator/Router, Finance) implementing a UI design → design QA → admin/client approval → prototype build → prototype QA → admin/client approval → M2 (20%) finance milestone → Admin-verified payment gate → Phase 5 pipeline, all wrapped in an Orchestrator/Router contract.

**Nothing in this pipeline is built yet.** But the repo is not starting from zero either: there is a real, mature foundation to build on in three specific places, and a well-known repo-wide failure pattern ("built but unreachable") that must be actively guarded against everywhere else.

### What already exists and is genuinely wired up

1. **Phase 3 design baseline is real, not aspirational.** `projects.design_token_sets` (`supabase/migrations/20260920000000_the_tokens_phase_four_inherits.sql`), `projects.theme_options`, and `projects.screens` are live tables with real application-layer readers/writers (`src/modules/projects/design.ts:525`, `src/modules/projects/queries.ts:1941`). The migration's own inline comment says "Phase 4 inherits them rather than recreating them." **Phase 4 UI work does not start from zero** — this directly answers the audit's flagged risk.
2. **Event/job/outbox system is real and trustworthy.** `src/lib/events/catalog.ts` follows a strict "only list what's real" house rule, backed by ~230 migrations of outbox/dispatch/retry infrastructure and a live cron-driven runner (`app/api/jobs/run/route.ts`). Phase 4 should register its new events here, not build a parallel mechanism.
3. **M1 (30%) milestone-invoicing engine is real and end-to-end**, including invoice generation, payment matching, Admin verification (`app/(internal)/invoices/verify/page.tsx`), and a server-enforced (not just UI-hidden) gate: `invoice.paid` → `projects:unlockNextMilestone`. This is the single strongest precedent for building M2's Admin-verification gate — the exact mechanism the Finance spec demands (proof ≠ verified, only Admin action opens the next stage) already exists in the codebase for a different milestone. Extend it; do not reinvent it.
4. **A generic producer≠verifier contract already exists**: `src/modules/agents/verification.ts` enforces that only a declared verifier (QA) can issue a verdict, and an agent cannot certify its own work. This is directly reusable scaffolding for the "Designer cannot self-pass QA" / "Prototype Agent cannot self-approve" / "QA cannot grant Admin/client approval" rules that recur in five of the seven specs.
5. **A reusable Admin review-UI template exists**: the Phase 3 approval-permalink feature (`app/(internal)/approvals/[requestId]/page.tsx`, commit `ef7a049`) is structurally close to what Admin UI/Prototype review screens need (CONFIRM/EDIT decision, exact-version reference, decision history).

### What is partial

- All 6 Phase 4 agents (`project_manager`, `ui_designer`, `ui_prototype`, `quality_assurance`, `finance`, `orchestrator`) are **typed and structurally validated** in `src/modules/agents/registry.ts` (13 agents total registry-wide), several with plausible tool bindings already declared. But per the registry's own comment, all of them except `requirement_collector` are **seeded disabled** — no evidence any of the six has ever actually executed. Tool lists in code are aspirational bindings, not live capability. This matters because it means Phase 4 cannot assume "the agent exists, just wire the workflow" — enabling + actually exercising each agent end-to-end is itself part of the work.
- The Admin agent-registry views (`app/(internal)/agents/*`) are real but read-only by design (a prior cross-tenant bug forced this), so they are a good template, not a ready-made write surface.
- `quality_assurance` is further behind than the other five: it has `tools: []` with no aspirational bindings at all, unlike the core/ops-layer agents. The spec's "QA/Prototype Validation Agent" may need to be a distinct capability/sub-role of this agent rather than a straight rename — flagged as a design decision, not just a build task.

### What is fully missing

- Every Phase-4-named database entity: `Phase4Workspace`, `UIVersion`, `UIScreenVersion`, `DesignQAReport`, `PrototypeBuild`, `PrototypeQARun`, `PrototypeDefect`, `FinancialMilestone` (M2-specific), `PaymentVerification` (M2-specific), and all the rest listed in the traceability matrix. None exist in `supabase/migrations/` under these or equivalent names.
- Every Phase-4-named event: `Phase4Started`, `UIDesignReady`, `UIDesignQAPassed`, `AdminUIApproved`, `ClientUIApproved`, `PrototypeBuildReady`, `PrototypeQAPassed`, `Phase4Completed`, `M2PaymentVerified`, etc. None appear in `src/lib/events/catalog.ts`.
- The Orchestrator/Router itself: no dispatch/routing module exists anywhere in `src/` or `app/`. The only Phase 4 agent for which there isn't even a name-level placeholder is the routing *engine* (as opposed to the `orchestrator` agent identity, which is typed but empty by design).
- All Admin UI panels specific to Phase 4 (UI Coverage, Design QA, Prototype Builds, Prototype QA, M2 Overview/Verification Queue, Routing Dashboard, etc.) — the closest existing things are generic siblings (`qa/page.tsx`, `finance/*`, `invoices/*`, approvals permalink) that would need Phase-4-specific extensions, not the panels themselves.
- All test suites — 152+ named test cases across the 4 core specs (60 + 28 + 32 + 32), plus 36 Finance and ~40 Orchestrator tests. None found.
- The M2 (20%), M3 (30%), M4 (20%) milestones. Only M1 (30%) exists in the finance engine today.

### What is broken/disconnected

- Nothing is "broken" in the sense of code that runs incorrectly — because none of the Phase 4-specific code exists yet, there is nothing to be broken. The relevant risk category here is **disconnection by design**: all six Phase 4 agents are typed with tool bindings that look complete in `registry.ts` but are inert because they're disabled in the database. Anyone reading `registry.ts` in isolation could reasonably (and wrongly) conclude these agents are functional. This is exactly the repo's documented "built but unreachable" failure mode, present pre-emptively for Phase 4's own agents before a line of Phase 4 logic is written.

### Flag: is there a Phase 3 UI/design baseline to build on?

**Yes.** `projects.design_token_sets`, `projects.theme_options`, and `projects.screens` are real, migrated, RLS-protected tables with real application-layer read/write code, and the newest of the three migrations is explicitly commented as being for Phase 4's benefit. Phase 4 UI work should treat this as its starting input, exactly as all 7 specs assume. This removes what would otherwise be the single largest schedule risk (discovering mid-Phase-4 that there's no real Phase 3 output to consume).

The one gap within this good-news finding: there is no Admin UI panel yet to browse/manage this baseline (no `phase-three-panel.tsx` equivalent exists alongside the existing `phase-two-panel.tsx`), so Task 2's "Baseline Loader" (Impl P4-03) needs both a data-loading function and a first-time Admin-visible surface.

### Spec requirements that conflict with existing architecture

1. **QA role granularity.** The specs treat "Design QA" and "Prototype Validation QA" as conceptually described within a single QA/Prototype Validation Agent document, while the Implementation Plan's Roles table also names a generic "QA Agent/QA capability." The current registry has exactly one `quality_assurance` agent with no sub-capability model. Building two independent Phase-4 QA gates (Design QA and Prototype QA) plus the pre-existing generic QA dashboard (`app/(internal)/qa/page.tsx`) on top of one undifferentiated agent identity risks conflating three things that the specs treat as distinct review stages with distinct evidence trails. Recommend an explicit capability/task-type split (e.g. `quality_assurance` agent with `taskType: 'design_qa' | 'prototype_qa' | ...`) rather than three parallel QA identities.
2. **Orchestrator vs. existing job runner.** The specs describe a capability-registry-driven, model/provider-agnostic Orchestrator that makes a `RoutingDecision` per task with cost/quality/latency policy. The current system's closest analog, `app/api/jobs/run/route.ts`, is a single cron-driven job runner that imports concrete handler functions directly — there is no dynamic agent/model selection layer at all today. This isn't a contradiction so much as a scale gap: the Orchestrator spec assumes infrastructure (agent capability registry, model/provider abstraction, routing decision persistence) that would be genuinely new architecture, not an extension of the existing job runner. Treat ORCH as the largest, least-precedented piece of Phase 4.
3. **"20/30/20/30" vs. current single-milestone (M1) implementation.** The Finance spec assumes the 30/20/30/20 structure is a known, pre-existing global concept that this document merely activates M2 within. In the actual repo, only M1 is implemented; there is no generic "N milestones with configurable percentages" abstraction yet — `finance:generateM1Invoice` appears to be M1-specific code, not a parameterized "generate milestone N invoice" function. Recommend checking `src/modules/finance/ladder.ts` (not read in full this pass) before assuming a trivial parameter change enables M2 — if the M1 logic is hardcoded rather than milestone-generic, this is a small-but-real refactor prerequisite.

## Biggest structural risk

**All six Phase 4 agents are typed placeholders, not running software, and the one piece of infrastructure every one of them depends on — a real Orchestrator/Router — does not exist at all.** The specs are written as if PM, UI Designer, Prototype, QA, and Finance are agents that can be "activated" and will then behave correctly inside a routing/permission/retry framework. In reality: (a) only `requirement_collector` has ever run in production across all 13 registered agents, (b) the `orchestrator` identity is deliberately empty (`tools: []`, `handoffTargets: []`) by prior design decision, and (c) there is no routing/dispatch code anywhere to enable it against. Every other gap in this audit (missing tables, missing events, missing Admin UI) is buildable in a fairly mechanical way by extending existing real patterns (the M1 finance engine, the outbox/catalog system, the approvals-permalink UI). The Orchestrator is the one component with no existing precedent to extend, and every other agent's Phase 4 work is specified as flowing *through* it. Building the five specialist agents' logic before the Orchestrator exists would recreate the exact "built but unreachable" pattern this codebase has already fought once (per prior session memory, `ADM-82`/agent-layer reality) — five more agents with correct-looking code and zero real execution path.

## Recommended implementation order (tailored to actual gaps, not spec's 0-35 stage numbering)

1. **Events + minimal Phase4Workspace/state machine first** (extends real `catalog.ts`/outbox — lowest risk, no architecture invention). Gives every other piece something real to react to and a place to persist state, so later stages aren't tempted to fake status via UI-only flags.
2. **Orchestrator/Router MVP**, scoped down from the full 40-item spec to: capability registry (reuse `registry.ts` + a `taskType` filter), a routing-decision record, and the QA-independence guard (reuse `verification.ts`'s existing producer≠verifier logic — this is the one guard with real precedent). Do not build the full model/provider cost-routing layer yet; hardcode provider selection initially and note it as a known simplification, matching the specs' own "model-agnostic, but configuration not hard business logic" principle without over-building day one.
3. **UI Designer Agent against the real Phase 3 baseline** (`design_token_sets`/`theme_options`/`screens`) — enable the already-typed `ui_designer` agent, build `UIVersion`/`UIScreenVersion` tables extending the existing screens schema, add Design QA as a `quality_assurance` task type, and reuse the approvals-permalink UI pattern for Admin/Client review.
4. **Prototype Agent + Prototype QA**, gated on step 3's UI lock. This is the most externally-dependent stage (build tooling, signing credentials) — flag manual/external blockers early per the specs' own guidance rather than discovering them mid-build.
5. **PM Agent communication layer**, reusing `src/modules/crm/handlers.ts` conventions (e.g., model a `handlePhaseFourCompleted` alongside the existing `handlePhaseThreeCompleted`) and the real WhatsApp send pipeline (`src/lib/whatsapp/send.ts`). This can be built in parallel with steps 3-4 once the events they emit are defined in step 1.
6. **Finance M2**, last, specifically because it has the strongest existing precedent (M1) and the smallest net-new surface area — extend the milestone-invoicing engine rather than build Finance logic from scratch, and reuse `/invoices/verify/page.tsx`'s Admin-verification pattern for the M2 gate. Confirm first whether `src/modules/finance/ladder.ts` already models milestones generically or is M1-hardcoded (unresolved in this audit — see conflict #3 above).
7. **Admin UI panels + full test suites**, built incrementally alongside each stage above rather than as a final phase, since the specs repeatedly emphasize that Admin visibility is itself a Definition-of-Done requirement per stage, not an afterthought.

Do not attempt to build PM, UI Designer, Prototype, QA, and Finance agent logic in parallel before step 2 lands — every spec explicitly routes cross-agent handoffs through Orchestrator/Coordination, and building the specialists first would just recreate five more "typed but never actually run" agents on top of the twelve that already exist in that state.
